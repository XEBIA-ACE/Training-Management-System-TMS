# Tasks: US-001

- [ ] T001 FR-US-001-001 (US-001-ac-1): The notifications module SHALL, before attempting to send any outbound email or SMS notification related to trainer allocation or deallocation, invoke the endpoint POST /api/v1/integration-acl/evaluate with the following parameters: providerType set to EMAIL (noting that this is ambiguous for SMS providers and must be interpreted consistently with provider configuration), providerId set to the configured identifier for the target email or SMS gateway, internalModule set to the notifications module identifier, and operation set to a value such as SEND_EMAIL or equivalent for the notification send operation; the module SHALL proceed with the notification send only when the AclEvaluationResult.allowed property is true.
- [ ] T002 FR-US-001-002 (US-001-ac-2): When the notifications module attempts to send a trainer allocation or deallocation notification and the POST /api/v1/integration-acl/evaluate call returns an AclEvaluationResult with allowed set to false, the ACL service SHALL populate the reason field with a clear, human-readable denial reason and SHALL NOT perform any provider routing or downstream provider invocation for that notification attempt, so that the calling notifications module can log and surface the access issue unambiguously.
- [ ] T003 FR-US-001-003 (US-001-ac-3): The ACL service SHALL allow configuration, via the CRUD endpoints on /api/v1/integration-acl, of ACL rules used for trainer allocation and deallocation notifications, including rateLimitPerMinute and dailyQuota constraints for the relevant EMAIL providerType and SEND_EMAIL (or equivalent) operation; during evaluation via POST /api/v1/integration-acl/evaluate, these configured limits SHALL be enforced consistently such that notification retry behaviour and overall throughput for trainer allocation and deallocation notifications do not exceed the defined limits.
- [ ] T004 FR-US-001-004 (US-001-ac-4): For every POST /api/v1/integration-acl/evaluate call made by the notifications module specifically for trainer allocation and deallocation notifications, the ACL service (or a shared cross-cutting component such as AclAuditLogger) SHALL create an audit log entry that records at least the calling internalModule, providerType, providerId, operation, and the resulting allow/deny decision (AclEvaluationResult.allowed), without persisting or otherwise exposing the actual notification content (e.g., subject, body, or SMS text).
- [ ] T005 FR-US-001-005 (US-001-ac-5): The ACL service SHALL ensure that the end-to-end latency of POST /api/v1/integration-acl/evaluate calls made as part of trainer allocation and deallocation notification flows remains low enough that these flows are not materially delayed by access control checks, by using the IntegrationPolicyEvaluator and any configured caching mechanisms; the precise latency threshold is not specified in the story and MUST be defined and measured by the implementation team as a non-functional criterion.
- [ ] T006 Verify US-001-ac-1: Before any outbound email or SMS notification related to trainer allocation or deallocation is sent by the notifications module, the notifications module invokes POST /api/v1/integration-acl/evaluate with providerType set to EMAIL, the appropriate providerId for the configured email or SMS gateway, internalModule set to the notifications module identifier, and operation set to a value such as SEND_EMAIL or equivalent, and receives an AclEvaluationResult with allowed set to true for authorized calls.
- [ ] T007 Verify US-001-ac-2: When the notifications module attempts to send a trainer allocation or deallocation notification and POST /api/v1/integration-acl/evaluate returns an AclEvaluationResult with allowed set to false, the ACL service returns a clear denial reason in the reason field without attempting any provider routing, enabling the caller to log and surface the access issue without ambiguity.
- [ ] T008 Verify US-001-ac-3: ACL rules required for trainer allocation and deallocation notifications, including any rateLimitPerMinute and dailyQuota constraints for the relevant EMAIL providerType and SEND_EMAIL operation, are configurable via the CRUD endpoints on /api/v1/integration-acl and are enforced consistently during evaluation so that notification retry and throughput behavior respects these limits.
- [ ] T009 Verify US-001-ac-4: Every evaluation call made by the notifications module for trainer allocation and deallocation notifications is logged internally via AclAuditLogger or equivalent cross cutting component so that allow and deny decisions for notification sends can be traced for audit and troubleshooting, without exposing notification content.
- [ ] T010 Verify US-001-ac-5: The ACL service maintains low latency for POST /api/v1/integration-acl/evaluate by using its IntegrationPolicyEvaluator and any configured caching so that notification sending flows for trainer allocation and deallocation are not materially delayed by access control checks.
