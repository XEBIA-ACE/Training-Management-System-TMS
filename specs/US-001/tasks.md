# Tasks: US-001

- [ ] T001 FR-US-001-001 (maps to US-001-ac-1): The Outbox Processing Service must consume trainer allocation and deallocation events written by application services to the transactional outbox table and publish each corresponding outbox entry to the internal message bus using the service’s event dispatcher and message publisher components, such that every valid outbox entry for allocation/deallocation is either successfully sent or marked with a terminal failure status.
- [ ] T002 FR-US-001-002 (maps to US-001-ac-1): The publication of allocation and deallocation events by the Outbox Processing Service must be implemented so that downstream internal notification services can receive and process these events in order to send trainer communications (email and configured SMS), acknowledging that the exact notification content and channel handling are out of scope for this service.
- [ ] T003 FR-US-001-003 (maps to US-001-ac-2): When publishing allocation or deallocation related outbox entries, the Outbox Processing Service must invoke its retry handler with exponential backoff, as defined in the C3 components, whenever a transient broker or infrastructure failure is detected, and must continue retrying until either the message is successfully published or a configured maximum retry limit is reached.
- [ ] T004 FR-US-001-004 (maps to US-001-ac-2): On each retry attempt for an allocation or deallocation related outbox entry, the Outbox Processing Service must update the associated OutboxEntry status and retry counter fields so that the current state (e.g., pending, in-progress, succeeded, failed, exhausted) and number of attempts are accurately reflected in persistent storage.
- [ ] T005 FR-US-001-005 (maps to US-001-ac-3): When an outbox entry related to trainer allocation notifications is successfully published to the internal message bus, the Outbox Processing Service must persist on the OutboxEntry entity: a success-indicating final status value, the final retryCount, a null or empty lastError, a processedAt timestamp, and the correlationId associated with that event.
- [ ] T006 FR-US-001-006 (maps to US-001-ac-3): When an outbox entry related to trainer allocation notifications reaches the maximum number of retries without successful publication, the Outbox Processing Service must persist on the OutboxEntry entity: a failure-indicating final status value that denotes retries are exhausted, the final retryCount, the lastError representing the most recent failure detail, a processedAt timestamp, and the correlationId associated with that event.
- [ ] T007 FR-US-001-007 (maps to US-001-ac-3): The persisted OutboxEntry fields status, retryCount, lastError, processedAt, and correlationId for trainer allocation and deallocation events must be stored in a way that downstream monitoring and audit tools can query them to infer the delivery outcomes of trainer notifications, without prescribing the exact storage technology or access mechanism.
- [ ] T008 FR-US-001-008 (maps to US-001-ac-4): The Outbox Processing Service must provide a GET /api/v1/outbox/stats HTTP endpoint that returns an OutboxStatistics representation containing processing statistics for trainer allocation and deallocation related outbox entries.
- [ ] T009 FR-US-001-009 (maps to US-001-ac-4): The OutboxStatistics model returned by GET /api/v1/outbox/stats must include, at a minimum, counts of allocation and deallocation outbox entries grouped by status (e.g., pending, in-progress, succeeded, failed, exhausted) and by event type (allocation vs deallocation), with any additional breakdowns treated as implementation detail.
- [ ] T010 FR-US-001-010 (maps to US-001-ac-4): The statistics provided by GET /api/v1/outbox/stats must be derived from the same persisted OutboxEntry data that the Outbox Processing Service uses for publishing and outcome tracking, such that the counts by status and event type accurately reflect the current backlog and failure levels for allocation and deallocation events at the time of the request, acknowledging potential minor delays due to eventual consistency.
- [ ] T011 FR-US-001-011 (maps to US-001-ac-5): The /health endpoint of the Outbox Processing Service must expose an aggregated health status that incorporates at least the health of outbox publishing for allocation and deallocation events, such as the ability to read from the transactional outbox store and to communicate with the internal message bus, without defining the exact health schema.
- [ ] T012 FR-US-001-012 (maps to US-001-ac-5): The /metrics endpoint of the Outbox Processing Service must expose metrics that allow operations teams to detect issues impacting trainer notification delivery for allocation and deallocation events, including metrics related to publishing success/failure rates and backlogs, without constraining the exact metric names or monitoring system integration.
- [ ] T013 Verify US-001-ac-1: When application services write trainer allocation or deallocation events to the transactional outbox table, the Outbox Processing Service must reliably publish these events to the internal message bus via its event dispatcher and message publisher components so that downstream notification services can react and send trainer communications.
- [ ] T014 Verify US-001-ac-2: When publishing allocation or deallocation related outbox entries, the Outbox Processing Service must use its retry handler and exponential backoff logic as described in the C3 components to automatically retry transient broker or infrastructure failures until either delivery succeeds or max retry limits are reached, updating the OutboxEntry status field accordingly.
- [ ] T015 Verify US-001-ac-3: When an outbox entry related to trainer allocation notifications ultimately succeeds or exhausts all retries, the Outbox Processing Service must persist the final status, retryCount, lastError, processedAt, and correlationId fields on the OutboxEntry entity so that downstream monitoring and audit tools can infer notification delivery outcomes for trainers.
- [ ] T016 Verify US-001-ac-4: The Outbox Processing Service must expose accurate processing statistics for allocation and deallocation related events via the GET /api/v1/outbox/stats endpoint and associated OutboxStatistics model, including counts by status and event type, to support monitoring of notification send failures and backlogs.
- [ ] T017 Verify US-001-ac-5: The Outbox Processing Service must ensure that health and metrics endpoints, including /health and /metrics, reflect the health of outbox publishing for allocation and deallocation events so that operations teams can detect issues impacting trainer notification delivery.
