# Tasks: US-003

## Implementation Tasks
- [ ] T001 FR-US-003-001 (US-003-ac-1): The POST /api/v1/trainers endpoint SHALL be accessible only to authenticated users with HR admin or super admin roles when creating an INTERNAL trainer (CreateTrainerRequest.type = INTERNAL). The service SHALL enforce all required fields defined for INTERNAL trainers, including but not limited to employeeId, and SHALL validate each field’s format according to the Trainer and CreateTrainerRequest schemas. If any required field is missing or any field fails schema validation, the service SHALL respond with HTTP 400 and a structured ErrorResponse that includes one or more FieldError entries identifying each invalid or missing field and an associated error message.
- [ ] T002 FR-US-003-002 (US-003-ac-2): The POST /api/v1/trainers endpoint SHALL be accessible only to authenticated users with HR admin or super admin roles when creating an EXTERNAL trainer (CreateTrainerRequest.type = EXTERNAL). For EXTERNAL trainer creation, the service SHALL enforce all required fields defined for EXTERNAL trainers, including at minimum email and locationId, and SHALL validate each field’s format as specified in the Trainer and CreateTrainerRequest schemas. If any required EXTERNAL-specific field is missing or any field is malformed, the service SHALL respond with HTTP 400 and an ErrorResponse describing the validation errors (the exact structure of the ErrorResponse is not further specified beyond what is stated in the acceptance criterion).
- [ ] T003 FR-US-003-003 (US-003-ac-3): During handling of POST /api/v1/trainers for any trainer type, the service SHALL perform uniqueness checks on trainer identifiers before persisting a new Trainer. Specifically: (a) if the request is for an INTERNAL trainer and any existing Trainer record (including both ACTIVE and INACTIVE trainers) already has the same employeeId as the one in the request, the service SHALL reject the request with HTTP 400 and an ErrorResponse that clearly indicates the conflict on the employeeId field; and (b) regardless of trainer type, if any existing Trainer record has the same email address as the one in the request, the service SHALL reject the request with HTTP 400 and an ErrorResponse that clearly indicates the conflict on the email field. The acceptance criterion does not specify behavior for other potential unique fields, so no additional uniqueness checks are mandated here.
- [ ] T004 FR-US-003-004 (US-003-ac-4): When processing POST /api/v1/trainers, if the CreateTrainerRequest.locationId maps to a location record in the core database that has an associated timezone, the service SHALL derive the Trainer.timezone value from that location and persist it as part of the Trainer aggregate. The derived timezone SHALL be used by downstream scheduling and reporting functionality that depends on Trainer.timezone for consistent behavior. Additionally, when handling PUT /api/v1/trainers/{trainerId}, if the request updates the trainer’s locationId to a different value that maps to a known timezone, the service SHALL recalculate Trainer.timezone based on the new location and persist the updated timezone. The acceptance criterion does not define behavior when the locationId does not map to a known timezone; such behavior is therefore out of scope for this requirement.
- [ ] T005 FR-US-003-005 (US-003-ac-5): Upon successful validation and uniqueness checking for POST /api/v1/trainers, the service SHALL create and persist a Trainer aggregate with its status field set to ACTIVE by default, without requiring any additional status-setting operation. Once created, this ACTIVE trainer SHALL be included in the results of GET /api/v1/trainers when that endpoint is invoked in a context that returns eligible trainers, and SHALL be considered by GET /api/v1/allocations/eligible-trainers when determining eligible trainers, subject to the trainer’s certifications and availability (which are referenced but not fully specified in this story).
- [ ] T006 FR-US-003-006 (US-003-ac-6): For every trainer successfully created via POST /api/v1/trainers, the service SHALL append an immutable audit event to the trainer-specific audit trail that is retrievable via GET /api/v1/trainers/{trainerId}/audit-logs. This audit event SHALL include at minimum: the actor who initiated the creation (e.g., user identifier or service principal as per the global audit model), a timestamp of the operation, the trainerId of the created trainer, and the non-document trainer profile fields captured at creation time (e.g., identity/contact details and other profile attributes, excluding any document contents). The service SHALL ensure that no sensitive document file contents from /api/v1/trainers/{trainerId}/documents are included in the audit event payload; only non-document metadata may be stored, consistent with the acceptance criterion.
- [ ] T007 FR-US-003-007 (US-003-ac-7): If, during POST /api/v1/trainers, the request fails due to schema or business validation errors (including required-field failures and format violations) or due to duplicate identifier checks (such as employeeId or email conflicts defined elsewhere in this story), the service SHALL still record an audit or unauthorized access log entry, in accordance with the system’s global audit model, representing the attempted but blocked trainer creation. This log entry SHALL be exposed via the relevant audit log endpoints such that consumers can see that a creation attempt occurred and was rejected; the acceptance criterion does not specify the exact shape of this log entry beyond consistency with the global audit model.

## Verification Tasks
- [ ] T008 Verify US-003-ac-1: When an HR admin or super admin calls POST /api/v1/trainers with a CreateTrainerRequest whose type is INTERNAL, the service must enforce required fields including employeeId and validate field formats according to the Trainer and CreateTrainerRequest schemas, rejecting invalid payloads with HTTP 400 and a structured ErrorResponse listing field level errors via FieldError entries.
- [ ] T009 Verify US-003-ac-2: When an HR admin or super admin calls POST /api/v1/trainers with a CreateTrainerRequest whose type is EXTERNAL, the service must enforce required fields including email and locationId and validate field formats as defined in the Trainer and CreateTrainerRequest schemas, rejecting any missing or malformed required data with HTTP 400 and ErrorResponse.
- [ ] T010 Verify US-003-ac-3: When processing POST /api/v1/trainers, the service must check for uniqueness of trainer identifiers such that if an INTERNAL trainer is being created and any existing Trainer record, regardless of its ACTIVE or INACTIVE status, already has the same employeeId, the request is rejected with HTTP 400 ErrorResponse indicating the conflicting employeeId field, and similarly if any existing Trainer has the same email as the requested profile, the request is rejected with HTTP 400 highlighting the email conflict.
- [ ] T011 Verify US-003-ac-4: When processing POST /api/v1/trainers with a locationId that corresponds to a known timezone in the core database, the service must derive and persist the Trainer.timezone field based on that location so that subsequent scheduling and reporting endpoints that use Trainer.timezone behave consistently; if the trainer is updated via PUT /api/v1/trainers/{trainerId} with a new locationId, the timezone must be recalculated and stored accordingly.
- [ ] T012 Verify US-003-ac-5: Upon successful creation of a trainer via POST /api/v1/trainers, the service must persist the Trainer aggregate with status set to ACTIVE by default and ensure that this trainer is returned in eligible states by GET /api/v1/trainers and considered by GET /api/v1/allocations/eligible-trainers, subject to their certifications and availability, without requiring an explicit status change call.
- [ ] T013 Verify US-003-ac-6: For every successful trainer creation through POST /api/v1/trainers, the service must append an immutable audit event recording the actor, timestamp, trainerId, and non document trainer profile fields to the trainer specific audit trail exposed via GET /api/v1/trainers/{trainerId}/audit-logs, and must ensure that no sensitive document file contents from /api/v1/trainers/{trainerId}/documents are included in the audit payload.
- [ ] T014 Verify US-003-ac-7: If validation or duplicate identifier checks fail during POST /api/v1/trainers, the service must still record an appropriate audit or unauthorized access log entry according to its global audit model so that attempted but blocked profile creations are visible via the relevant audit log endpoints.
