# Feature Specification: US-003

## User Scenarios & Testing
- **US-003**: When the client calls POST /api/v1/trainers with a payload to create a trainer, the HTTP API Controller Layer must invoke the Request Validation and Mapping component using ValidateAndMapCreateTrainer to enforce that all required fields for the specified trainer type (internal versus external) are present and correctly formatted, and must return a structured validation error response without persisting anything if validation fails.
- **US-003**: When ValidateAndMapCreateTrainer maps the incoming payload to a CreateTrainerCommand, the Trainer Application Service and Trainer Domain Services must enforce uniqueness constraints so that AddTrainer via the Trainer Repository is rejected with a domain or validation error if the Employee ID for an internal trainer or the Email for any trainer already exists on any active or inactive trainer record, and this error must be surfaced by the controller as a clear duplicate indication to the client.
- **US-003**: When a CreateTrainer command includes a selected location that can be resolved to a geographic region stored in the transactional database, Trainer Domain Services must derive an appropriate time zone value from that location and persist it as part of the trainer aggregate via the Trainer Repository so that downstream scheduling and notifications can use it.
- **US-003**: When CreateTrainer successfully persists a new trainer aggregate through the Trainer Repository, Trainer Domain Services must default the trainer status field to an Active value and the Trainer Application Service must ensure that subsequent SearchTrainers queries include this trainer in eligible search and allocation views that respect existing eligibility and conflict rules.
- **US-003**: On every successful trainer creation handled by the Trainer Application Service, the application layer must construct an audit event containing the acting user identity, timestamp, trainer identifier, and key non sensitive profile fields, and persist it via the AppendAuditEvent operation on the Audit Log Repository Interface so that an immutable audit trail of trainer creation is maintained without storing any document contents.
- **US-003**: For any failed trainer creation attempt caused by validation or duplicate detection, the ExceptionHandlingMiddleware and Request Validation and Mapping must translate errors into consistent HTTP responses while still ensuring that no partial trainer data is written via Trainer Repository and that no audit entry of a successful create is appended via the Audit Log Repository.

## Functional Requirements
- FR-US-003-001 (US-003-ac-1): The HTTP API Controller handling POST /api/v1/trainers SHALL invoke the Request Validation and Mapping component using the ValidateAndMapCreateTrainer operation for every incoming create-trainer payload, and this operation SHALL enforce presence and correct formatting of all required fields for the specified trainer type (internal versus external). If validation fails, the controller SHALL return a structured validation error response to the client and SHALL NOT persist any trainer-related data to the Trainer Repository as part of that request.
- FR-US-003-002 (US-003-ac-1): The structured validation error response for POST /api/v1/trainers validation failures SHALL include, at minimum, an indication that validation failed and a machine-parseable structure of one or more field-level or rule-level errors; the exact error schema is not specified by this story and MUST be defined consistently with the platform’s existing API error contract (ambiguity: error shape and HTTP status code are not defined here).
- FR-US-003-003 (US-003-ac-2): When ValidateAndMapCreateTrainer successfully maps the incoming payload to a CreateTrainerCommand, the Trainer Application Service together with Trainer Domain Services SHALL enforce uniqueness such that any AddTrainer operation via the Trainer Repository is rejected with a domain or validation error if (a) for an internal trainer, the Employee ID already exists on any active or inactive trainer record, or (b) for any trainer (internal or external), the Email already exists on any active or inactive trainer record.
- FR-US-003-004 (US-003-ac-2): When a trainer creation attempt is rejected due to the Employee ID or Email uniqueness rule, the HTTP API Controller SHALL surface this condition to the client as a clear duplicate indication in the HTTP response; the story does not specify the exact HTTP status code or error payload shape, which MUST be aligned with the platform’s standard duplicate/constraint violation response pattern (ambiguity: specific code and field naming are not defined).
- FR-US-003-005 (US-003-ac-3): When processing a CreateTrainer command whose selected location can be resolved to a geographic region stored in the transactional database, Trainer Domain Services SHALL derive an appropriate time zone value from that location and SHALL persist that time zone as part of the trainer aggregate via the Trainer Repository so that it is available for downstream scheduling and notification logic.
- FR-US-003-006 (US-003-ac-3): If the selected location on a CreateTrainer command cannot be resolved to a geographic region stored in the transactional database, this story does not specify the expected behavior for deriving or defaulting a time zone, and such behavior MUST be defined elsewhere (explicit gap/ambiguity).
- FR-US-003-007 (US-003-ac-4): Upon successful persistence of a new trainer aggregate through the Trainer Repository via CreateTrainer, Trainer Domain Services SHALL set the trainer status field to an Active value by default, without requiring the client to supply a status in the create request.
- FR-US-003-008 (US-003-ac-4): After a trainer is successfully created and persisted with status Active, the Trainer Application Service SHALL ensure that subsequent SearchTrainers queries include this trainer in search and allocation views that are defined to show eligible trainers, subject to the existing eligibility and conflict rules implemented by SearchTrainers; this story does not modify or restate those underlying rules (explicit dependency).
- FR-US-003-009 (US-003-ac-5): For every successful trainer creation handled by the Trainer Application Service, the application layer SHALL construct an audit event that includes at least: (a) the acting user identity, (b) a timestamp of the operation, (c) the unique trainer identifier of the newly created trainer, and (d) key non-sensitive profile fields (exact list to be defined consistently with privacy/security guidelines and excluding any document contents).
- FR-US-003-010 (US-003-ac-5): The Trainer Application Service SHALL persist each trainer-creation audit event by calling AppendAuditEvent on the Audit Log Repository Interface, and the resulting audit log entry SHALL be stored in an immutable form such that it constitutes an audit trail of trainer creation operations while explicitly NOT storing any trainer-related document contents (e.g., copies of contracts or uploaded files).
- FR-US-003-011 (US-003-ac-6): For any failed trainer creation attempt caused by validation errors or duplicate detection, the ExceptionHandlingMiddleware together with the Request Validation and Mapping component SHALL translate the underlying errors into consistent HTTP responses, aligned with the platform’s general API error handling conventions; the exact mapping of error types to HTTP status codes and payload shapes is not defined in this story and MUST be specified elsewhere (ambiguity: concrete mapping is unspecified).
- FR-US-003-012 (US-003-ac-6): In all cases where trainer creation fails due to validation errors or duplicate detection, the system SHALL guarantee that no partial trainer data is written via the Trainer Repository (i.e., no new or partially populated trainer aggregate is persisted) and SHALL guarantee that no audit entry representing a successful trainer create is appended via the Audit Log Repository for that request.
