# Feature Specification: US-003

## User Scenarios & Testing
- **US-003**: When a client calls POST /trainers with a TrainerCreateRequest whose type is internal, the TMS Core Application Service must invoke the ValidationEngine through TrainerAppService to enforce required fields and format validation specific to internal trainers, returning a 400 ErrorResponse with details if any mandatory field such as employeeId, name, or email is missing or malformed.
- **US-003**: When a client calls POST /trainers with a TrainerCreateRequest whose type is external, the TMS Core Application Service must invoke the ValidationEngine through TrainerAppService to enforce required fields and format validation specific to external trainers, at minimum requiring name, email, and type, and must return a 400 ErrorResponse with details when these are missing or incorrectly formatted.
- **US-003**: When handling POST /trainers, TrainerAppService must query TrainerRepository to ensure that the provided employeeId (for internal trainers) or email (for any trainer type) is unique across all existing trainer records, and must return HTTP 400 with an ErrorResponse indicating a validation or duplicate error if a conflict is found.
- **US-003**: When handling a successfully validated POST /trainers request that includes a locationId, TrainerAppService together with TrainerDomainService must derive and persist a timeZone value on the Trainer entity before saving via TrainerRepository, so that subsequent GET /trainers and related allocation/reporting endpoints return this timeZone field populated.
- **US-003**: When a trainer profile is successfully created via POST /trainers, the Trainer aggregate persisted through TrainerRepository must have its status field set to active by default, making the trainer immediately eligible to appear in results from GET /trainers when the status filter is active or all.
- **US-003**: For every successful trainer creation transaction through POST /trainers, TrainerAppService must use AuditLogClient to append an audit entry that records the actor identity from AuthContextProvider, a timestamp, the resourceType representing trainer, the new trainer id, an actionType representing create, and a summary or payload of key non sensitive fields, with this audit visible through the existing admin and audit search interfaces such as GET /admin/audit.
- **US-003**: If a POST /trainers request fails validation or uniqueness checks, the service must ensure via TransactionManager that no partial Trainer record is persisted in tmsDb, and that only audit entries appropriate for failed attempts, if any, are written without creating an inconsistent trainer profile.

## Functional Requirements
- FR-US-003-001 (US-003-ac-1): For requests to POST /trainers where TrainerCreateRequest.type = "internal", TMS Core Application Service must invoke ValidationEngine via TrainerAppService to validate internal-trainer-specific required fields and formats, and must return HTTP 400 with an ErrorResponse containing details when any mandatory field (including at least employeeId, name, or email) is missing or malformed; the exact full list of mandatory internal fields beyond these examples is not fully specified and must be treated as implementation-defined.
- FR-US-003-002 (US-003-ac-2): For requests to POST /trainers where TrainerCreateRequest.type = "external", TMS Core Application Service must invoke ValidationEngine via TrainerAppService to validate external-trainer-specific required fields and formats, must treat at minimum name, email, and type as mandatory, and must return HTTP 400 with an ErrorResponse containing details when any of these are missing or incorrectly formatted; any additional mandatory fields for external trainers are not specified and remain an open design choice.
- FR-US-003-003 (US-003-ac-3): For all POST /trainers requests, TrainerAppService must query TrainerRepository to check uniqueness such that (a) employeeId is unique among internal trainers and (b) email is unique across all trainers regardless of type, and if a duplicate employeeId or email is found it must reject the request with HTTP 400 and an ErrorResponse that identifies the condition as a validation or duplicate error, without proceeding to persist the Trainer entity.
- FR-US-003-004 (US-003-ac-4): For any POST /trainers request that passes validation and includes a non-null locationId, TrainerAppService together with TrainerDomainService must derive a timeZone value associated with that locationId, set this timeZone on the Trainer entity, and persist it via TrainerRepository so that subsequent reads of that trainer (including via GET /trainers and related allocation/reporting endpoints) return a populated timeZone field; the derivation logic or mapping source for timeZone from locationId is not specified and must be defined elsewhere.
- FR-US-003-005 (US-003-ac-5): Upon successful creation of a trainer profile through POST /trainers (i.e., after all validations and uniqueness checks pass and the entity is persisted), the Trainer aggregate saved via TrainerRepository must have status set to "active" by default, ensuring that this trainer is included in GET /trainers responses whenever status is filtered by active or all.
- FR-US-003-006 (US-003-ac-6): For every successful trainer creation transaction via POST /trainers, TrainerAppService must call AuditLogClient to append an audit entry that includes: (a) actor identity obtained from AuthContextProvider, (b) a timestamp, (c) a resourceType value representing a trainer resource, (d) the newly created trainer id, (e) an actionType value representing create, and (f) a summary or payload containing key non-sensitive trainer fields, and this audit record must be retrievable through existing admin and audit search interfaces such as GET /admin/audit; the precise set of fields considered non-sensitive is not defined and must be determined by security/privacy guidelines.
- FR-US-003-007 (US-003-ac-7): For any POST /trainers request that fails either validation or uniqueness checks, the service must use TransactionManager (or equivalent transactional mechanism) to guarantee that no partial or intermediate Trainer data is written to tmsDb and must ensure that only audit entries appropriate for failed attempts, if any are written, are persisted such that no inconsistent or partially created trainer profile can exist; the specific content and presence of audit entries for failed attempts is not fully specified and must follow existing audit policies.
