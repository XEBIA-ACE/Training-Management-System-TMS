# Feature Specification: US-003

## User Scenarios & Testing
- **US-003**: When the client calls POST /trainers with a TrainerCreateRequest, the REST controller and Request Validation component must enforce required fields based on the type field such that INTERNAL trainers require a non empty employeeId while EXTERNAL trainers do not, and email, name, location, and type are always present and correctly formatted, returning an ErrorResponse with field level details on any violation.
- **US-003**: When handling POST /trainers, the Trainer Application Service and Trainer Repository must enforce uniqueness of email across all trainer records regardless of status ACTIVE or INACTIVE and additionally enforce uniqueness of employeeId for INTERNAL trainers, returning a 400 response with an ErrorResponse that identifies the conflicting field when a duplicate is detected.
- **US-003**: Upon successful creation of a trainer via POST /trainers, the Trainer Application Service must persist the trainer with status set to ACTIVE in the underlying TrainerResponse.status field so that subsequent GET /trainers queries with status ACTIVE include the new trainer without requiring a separate status change call.
- **US-003**: When a valid location value is supplied in TrainerCreateRequest and POST /trainers succeeds, the Trainer Application Service and underlying domain must derive and persist an appropriate timeZone value in the TrainerResponse.timeZone field, using platform configuration or scheduling domain rules, so that downstream scheduling and notification components can rely on this stored timezone without additional derivation at read time.
- **US-003**: For each successful trainer creation through POST /trainers, the REST controller or Trainer Application Service must invoke the Audit Logging Component so that an immutable AuditEvent with module set to TRAINER, actionType indicating create, actorUserId equal to the authenticated user, timestamp, and non sensitive key fields such as trainerId, type, employeeId when present, email, location, and status is appended to the audit log via /audit/events or the AuditLogRepository.
- **US-003**: All validation and duplicate constraint failures during POST /trainers must be returned using the standard ErrorResponse schema with code values such as VALIDATION_ERROR or a duplicate specific code and populated details entries for each invalid field, consistent with the shared error handling rules in the Training Management Core Service.

## Functional Requirements
- FR-US-003-001 (US-003-ac-1): The POST /trainers REST controller and associated request validation must require that TrainerCreateRequest includes non-empty values for email, name, location, and type for all trainers, and additionally a non-empty employeeId when type is INTERNAL, and must validate that these fields are correctly formatted according to the shared validation rules; on any violation, the API must return an ErrorResponse with field-level details for each invalid or missing field as described in US-003-ac-1.
- FR-US-003-002 (US-003-ac-2): When processing POST /trainers, the Trainer Application Service in conjunction with the Trainer Repository must enforce that email is unique across all trainer records irrespective of their status (ACTIVE or INACTIVE) and that employeeId is unique among INTERNAL trainers; if any uniqueness constraint is violated, the service must return HTTP 400 with an ErrorResponse that identifies which field(s) (email and/or employeeId) caused the conflict, as described in US-003-ac-2.
- FR-US-003-003 (US-003-ac-3): On successful processing of POST /trainers (i.e., all validations and uniqueness checks pass), the Trainer Application Service must persist the new trainer record with status set to ACTIVE and expose this value via TrainerResponse.status such that subsequent GET /trainers queries filtered with status ACTIVE will include the newly created trainer without requiring any additional status update, as described in US-003-ac-3.
- FR-US-003-004 (US-003-ac-4): When TrainerCreateRequest contains a valid location and POST /trainers completes successfully, the Trainer Application Service and underlying domain logic must derive an appropriate timeZone value based on the supplied location using platform configuration or scheduling-domain rules and must persist this value so that it is available in TrainerResponse.timeZone for later reads, eliminating the need to re-derive time zone at read time, as described in US-003-ac-4; any ambiguity in how validity of location or the derivation rules are defined must be resolved outside this requirement.
- FR-US-003-005 (US-003-ac-5): For every successfully created trainer via POST /trainers, the REST controller or Trainer Application Service must call the Audit Logging Component to append an immutable AuditEvent with module set to TRAINER, actionType indicating create, actorUserId equal to the authenticated user, a timestamp, and non-sensitive key fields including trainerId, type, employeeId when present, email, location, and status, via the /audit/events API or AuditLogRepository, as described in US-003-ac-5.
- FR-US-003-006 (US-003-ac-6): For all validation and duplicate-constraint failures encountered during POST /trainers processing, the API must return the platform-standard ErrorResponse schema with an error code such as VALIDATION_ERROR or a duplicate-specific code and must populate the details collection with entries for each invalid or conflicting field, in a manner consistent with the shared error-handling rules of the Training Management Core Service, as described in US-003-ac-6.
