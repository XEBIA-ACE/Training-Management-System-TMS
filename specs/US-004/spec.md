# Feature Specification: US-004

## User Scenarios & Testing
- **US-004**: In the Trainer Management micro frontend trainer-mgmt-web, the trainer detail and edit routes at path pattern /trainers/:trainerId and /trainers/:trainerId/edit must render and allow modification of a discrete status field that maps to the backend trainer status attribute, without clearing or overwriting any non status profile fields in the form state when toggled between active and inactive.
- **US-004**: The Trainer Management micro frontend trainer-mgmt-web must call the trainer-service status update endpoint that persists status changes while leaving all other trainer profile data unchanged, and it must refresh its local view model from the updated trainer record after a successful response so that no profile information appears lost to the user.
- **US-004**: On all allocation related UIs in the Trainer Allocation micro frontend trainer-allocation-web, the trainer selection controls used on routes matching /allocation, /allocation/customer/:customerId, and /allocation/workshop/:workshopId must only request and display trainers whose status is active according to trainer-service data, thereby excluding inactive trainers from selection lists for new allocations.
- **US-004**: When a user attempts to allocate a trainer who is currently inactive, the Trainer Allocation micro frontend trainer-allocation-web must detect this either from the pre filtered list or from an allocation-service error response and must block completion of the allocation flow, displaying a clear inline error message explaining that inactive trainers cannot be allocated.
- **US-004**: When a trainer whose status was inactive becomes active again, the Trainer Allocation micro frontend trainer-allocation-web must ensure that subsequent trainer search or lookup calls against trainer-service or trainer-allocation-service include that trainer in results when they satisfy other eligibility filters such as required certifications and availability, and the UI must reflect this by making the trainer selectable.
- **US-004**: The Trainer Management and Trainer Allocation micro frontends must propagate the authenticated user identity to the audit-service when invoking any existing audit logging integration for trainer status changes, so that audit entries include the actor identifier along with the trainer identifier, previous status, new status, and timestamp as returned by the audit-service.

## Functional Requirements
- FR-US-004-001 (maps US-004-ac-1): The trainer-mgmt-web application shall expose, on the trainer detail and edit routes /trainers/:trainerId and /trainers/:trainerId/edit, a discrete trainer status field (e.g., enumerated Active/Inactive) that is directly bound to the backend trainer status attribute and can be modified by authorized users without causing any other non-status trainer profile fields already present in the edit form state to be cleared, reset, or overwritten when the status value is toggled.
- FR-US-004-002 (maps US-004-ac-1): When the user changes the discrete trainer status field on /trainers/:trainerId or /trainers/:trainerId/edit and then saves the record, trainer-mgmt-web shall preserve all non-status profile field values that were present in the form prior to the status change, such that the only field difference attributable to the status change operation is the trainer status attribute itself.
- FR-US-004-003 (maps US-004-ac-2): On submission of a status change for a trainer, trainer-mgmt-web shall invoke the trainer-service status update endpoint, passing the trainer identifier and new status value, and shall rely on that endpoint to persist the status change while leaving all other trainer profile data unchanged server-side; the frontend shall not attempt to update or resend non-status profile fields as part of this status-only operation unless explicitly required by the endpoint contract (ambiguity: the exact shape of the trainer-service status update endpoint payload is not defined here and must be confirmed separately).
- FR-US-004-004 (maps US-004-ac-2): After receiving a successful response from the trainer-service status update endpoint, trainer-mgmt-web shall request or otherwise obtain the updated trainer record from trainer-service and refresh its local view model so that the UI re-renders with the current status and unchanged profile fields, ensuring that no trainer profile information appears to be lost or reverted from the user’s perspective.
- FR-US-004-005 (maps US-004-ac-3): In trainer-allocation-web, all trainer selection controls rendered on allocation-related routes /allocation, /allocation/customer/:customerId, and /allocation/workshop/:workshopId shall obtain trainer lists only from trainer-service or trainer-allocation-service queries that are filtered to include trainers whose status is Active according to trainer-service data, and shall exclude any trainers whose status is not Active from the selectable options for initiating new allocations.
- FR-US-004-006 (maps US-004-ac-3): Trainer-allocation-web shall ensure that, on the allocation-related routes /allocation, /allocation/customer/:customerId, and /allocation/workshop/:workshopId, UI components (dropdowns, search results, lists, etc.) do not render or allow selection of trainers that are marked Inactive in trainer-service at the time of data retrieval, so that inactive trainers are not available for new allocation creation.
- FR-US-004-007 (maps US-004-ac-4): If, in spite of pre-filtering, a user flow in trainer-allocation-web results in an attempt to allocate a specific trainer identifier that is currently Inactive (for example, due to stale client state or an allocation-service validation failure), trainer-allocation-web shall detect this condition based on either the pre-filtered trainer list state or an explicit error response from allocation-service, and shall block completion of the allocation (i.e., shall not persist or display the allocation as successful).
- FR-US-004-008 (maps US-004-ac-4): When trainer-allocation-web blocks an allocation attempt because the selected trainer is Inactive, it shall display a clear inline error message in the allocation UI, adjacent to or associated with the trainer selection or submission control, explaining that inactive trainers cannot be allocated; the exact wording and placement of this message may vary by UX design but must unambiguously communicate that the trainer’s inactive status is the cause (ambiguity: specific copy and localization requirements are not defined here).
- FR-US-004-009 (maps US-004-ac-5): When a trainer’s status changes from Inactive to Active in trainer-service, trainer-allocation-web shall, on subsequent use of trainer search or lookup features on allocation-related routes, call trainer-service and/or trainer-allocation-service in a way that no longer excludes that trainer on the basis of status, so that they can appear in results whenever they meet all other applicable eligibility filters such as required certifications and availability.
- FR-US-004-010 (maps US-004-ac-5): Provided that a previously inactive trainer now has status Active in trainer-service and satisfies other configured eligibility criteria (e.g., correct certifications and availability according to the services’ responses), trainer-allocation-web shall render that trainer as a selectable option in trainer search or selection UI components on allocation-related routes, with interaction behavior equivalent to other eligible active trainers.
- FR-US-004-011 (maps US-004-ac-6): Whenever trainer-mgmt-web initiates a trainer status change (e.g., from Active to Inactive or Inactive to Active) and triggers any existing audit logging integration, it shall propagate the authenticated user’s identity to the audit-service along with the trainer identifier, previous status, and new status, so that the resulting audit entry contains the actor identifier in addition to trainer and status change information; the precise mechanism for propagating identity (headers, tokens, or payload fields) is subject to the existing audit integration contract and is not specified here (ambiguity left deliberate).
- FR-US-004-012 (maps US-004-ac-6): Whenever trainer-allocation-web is involved in initiating or mediating a trainer status change that is audit-logged (for example, where allocation flows or admin actions from allocation context trigger status updates), it shall ensure the authenticated user identity is provided to the audit-service along with the trainer identifier, previous status, new status, and timestamp as required by the existing audit logging integration, so that audit entries record who performed the change; the exact set of status-change entry points in trainer-allocation-web that must log to audit-service is not explicitly enumerated here and must be derived from the integration design (ambiguity preserved).
