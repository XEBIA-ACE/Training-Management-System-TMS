# Feature Specification: US-004

## User Scenarios & Testing
- **US-004**: When an HR_ADMIN or SUPER_ADMIN calls PATCH /api/v1/trainers/{trainerId}/status with a valid status value such as ACTIVE or INACTIVE, the service updates only the Trainer.status field and related status metadata while preserving all other Trainer profile fields unchanged, returning the updated Trainer representation.
- **US-004**: When a trainer’s status is set to INACTIVE via PATCH /api/v1/trainers/{trainerId}/status, subsequent calls to GET /api/v1/trainers and GET /api/v1/allocations/eligible-trainers must exclude that trainer from default search and eligibility results unless the caller explicitly filters for INACTIVE or ALL, ensuring they cannot be selected for new allocations.
- **US-004**: When a client attempts to allocate a trainer whose Trainer.status is INACTIVE using POST /api/v1/allocations, the service must reject the request with HTTP 400 or 403 using ErrorResponse, include a clear business message indicating the trainer is inactive and cannot be allocated, and must not create an Allocation record.
- **US-004**: When a previously inactive trainer is reactivated to ACTIVE via PATCH /api/v1/trainers/{trainerId}/status, subsequent calls to GET /api/v1/trainers and GET /api/v1/allocations/eligible-trainers calls must again consider that trainer as eligible for search and allocation results provided other filters such as certifications and availability match, using existing Trainer.certifications and availability logic.
- **US-004**: Every successful or failed attempt to change a trainer’s status via PATCH /api/v1/trainers/{trainerId}/status must append an immutable audit entry, accessible via GET /api/v1/trainers/{trainerId}/audit-logs and or /api/v1/admin/audit-logs, that records the trainer identifier, previous status, new status, acting user, timestamp, and outcome such as SUCCESS or DENIED.
- **US-004**: If a caller without HR_ADMIN or SUPER_ADMIN role invokes PATCH /api/v1/trainers/{trainerId}/status, the service must deny the request with HTTP 403 using ErrorResponse and record the denied attempt in the unauthorized access logs exposed via GET /api/v1/admin/unauthorized-access-logs, without changing the trainer’s status.
- **US-004**: rationale

## Functional Requirements
- FR-US-004-AC1-001: The PATCH /api/v1/trainers/{trainerId}/status endpoint SHALL be callable only by users with HR_ADMIN or SUPER_ADMIN role when updating a trainer’s status (per US-004-ac-1).
- FR-US-004-AC1-002: When PATCH /api/v1/trainers/{trainerId}/status is invoked with a valid status value (e.g., ACTIVE, INACTIVE), the service SHALL update only the Trainer.status field and any defined status-related metadata fields (e.g., statusChangedAt, statusChangedBy), and SHALL NOT modify any other Trainer profile fields (per US-004-ac-1).
- FR-US-004-AC1-003: Upon successful status update via PATCH /api/v1/trainers/{trainerId}/status, the service SHALL return the full, updated Trainer representation in the response body (per US-004-ac-1).
- FR-US-004-AC2-001: After a trainer’s status has been set to INACTIVE via PATCH /api/v1/trainers/{trainerId}/status, subsequent calls to GET /api/v1/trainers without an explicit status filter SHALL exclude that trainer from the returned list (per US-004-ac-2).
- FR-US-004-AC2-002: After a trainer’s status has been set to INACTIVE, subsequent calls to GET /api/v1/allocations/eligible-trainers without an explicit status filter SHALL exclude that trainer from the eligible trainers list (per US-004-ac-2).
- FR-US-004-AC2-003: The GET /api/v1/trainers and GET /api/v1/allocations/eligible-trainers endpoints SHALL include support for explicit status filters that allow callers to request INACTIVE or ALL statuses, and when such filters include INACTIVE or ALL, inactive trainers MAY appear in the results subject to other filters (per US-004-ac-2; note: the exact filter parameter naming and syntax is not specified in the story and must be defined during design).
- FR-US-004-AC2-004: While a trainer is INACTIVE, the system SHALL prevent that trainer from being selected for any new allocation flows that depend on the default eligible-trainer search behavior (per US-004-ac-2; the story does not define whether any non-default or direct-allocation paths may still reference an inactive trainer, which must be clarified separately).
- FR-US-004-AC3-001: When POST /api/v1/allocations is called to allocate a trainer whose current Trainer.status is INACTIVE, the service SHALL reject the request with either HTTP 400 or HTTP 403 and SHALL NOT create any Allocation record (per US-004-ac-3; the story does not specify which of 400 vs 403 applies in which situation).
- FR-US-004-AC3-002: For a rejected allocation attempt due to inactive trainer status, the service’s ErrorResponse payload SHALL include a business-level message that clearly states the trainer is inactive and cannot be allocated (per US-004-ac-3).
- FR-US-004-AC4-001: When a trainer previously marked INACTIVE is updated to ACTIVE via PATCH /api/v1/trainers/{trainerId}/status, subsequent calls to GET /api/v1/trainers SHALL once again include that trainer in search results whenever the applied filters (including any status filter) would normally include ACTIVE trainers (per US-004-ac-4).
- FR-US-004-AC4-002: When a trainer previously marked INACTIVE is updated to ACTIVE via PATCH /api/v1/trainers/{trainerId}/status, subsequent calls to GET /api/v1/allocations/eligible-trainers SHALL consider that trainer eligible for inclusion in results, provided they meet existing filters such as certifications and availability (per US-004-ac-4).
- FR-US-004-AC4-003: The reactivation of a trainer to ACTIVE SHALL NOT alter or bypass existing Trainer.certifications and availability logic; eligibility after reactivation remains subject to the same rules as for other ACTIVE trainers (per US-004-ac-4).
- FR-US-004-AC5-001: Every attempt (successful or failed) to change a trainer’s status via PATCH /api/v1/trainers/{trainerId}/status SHALL create an immutable audit entry that cannot be modified or deleted once written (per US-004-ac-5).
- FR-US-004-AC5-002: Each status-change audit entry SHALL record at minimum: trainer identifier, previous status, new status, acting user identifier, timestamp of the attempt, and the outcome value (e.g., SUCCESS or DENIED) (per US-004-ac-5).
- FR-US-004-AC5-003: Status-change audit entries SHALL be retrievable via GET /api/v1/trainers/{trainerId}/audit-logs for trainer-specific access and via GET /api/v1/admin/audit-logs for global or admin-level access (per US-004-ac-5; the story does not specify pagination, filtering, or retention rules for these endpoints).
- FR-US-004-AC6-001: If PATCH /api/v1/trainers/{trainerId}/status is invoked by a caller that does not have HR_ADMIN or SUPER_ADMIN role, the service SHALL respond with HTTP 403 and SHALL NOT modify the trainer’s status (per US-004-ac-6).
- FR-US-004-AC6-002: For unauthorized status-change attempts, the service SHALL use the standard ErrorResponse structure in the HTTP 403 response (per US-004-ac-6; the exact ErrorResponse schema is referenced but not defined in this story).
- FR-US-004-AC6-003: Every denied attempt to change a trainer’s status due to insufficient role SHALL be recorded in an unauthorized access log that is exposed via GET /api/v1/admin/unauthorized-access-logs (per US-004-ac-6; the story does not define log retention, filtering, or correlation identifiers).
- FR-US-004-AC7-001: The story description and prior criteria collectively indicate that trainer activation/inactivation is implemented primarily via SVC-007-related endpoints (e.g., PATCH /api/v1/trainers/{trainerId}/status, GET /api/v1/allocations/eligible-trainers, POST /api/v1/allocations, trainer-level and admin-level audit endpoints) and that these endpoints MUST work together to ensure inactive trainers remain non-allocatable while preserving historical records for reporting and audit (per US-004-ac-7 "rationale"; note: this criterion is a rationale and does not introduce additional, independently testable behavior beyond cross-endpoint consistency).
