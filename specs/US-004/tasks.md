# Tasks: US-004

- [ ] T001 FR-US-004-001 (US-004-ac-1): The Training Management Core Service SHALL expose POST /trainers/{trainerId}/status that, when invoked with a syntactically and semantically valid TrainerStatusChangeRequest and by an authenticated user possessing the required trainer lifecycle permission, updates ONLY the TrainerResponse.status field for the targeted trainer record between the values ACTIVE and INACTIVE in the underlying trainer repository, leaving all other trainer profile fields and identifiers unchanged.
- [ ] T002 FR-US-004-002 (US-004-ac-1): POST /trainers/{trainerId}/status SHALL NOT allow status transitions to any value other than ACTIVE or INACTIVE; any attempt to set a different status value is out of scope/undefined in this story and MUST be treated as invalid according to centralized request validation rules (exact error semantics may be specified elsewhere).
- [ ] T003 FR-US-004-003 (US-004-ac-2): When a trainer’s status has been set to INACTIVE via POST /trainers/{trainerId}/status, subsequent calls to GET /trainers without an explicit status filter SHALL, by default, exclude that trainer from the returned list of trainers.
- [ ] T004 FR-US-004-004 (US-004-ac-2): Any trainer search mechanism used internally by POST /allocations for determining eligible trainers SHALL, by default, exclude trainers whose TrainerResponse.status is INACTIVE from eligibility and list results, unless an explicit status filter or INACTIVE_DATA.VIEW-style permission is applied, in accordance with centralized visibility rules (the precise visibility rules are defined outside this story and must be honored as-is).
- [ ] T005 FR-US-004-005 (US-004-ac-3): If POST /allocations is invoked to allocate a trainer whose TrainerResponse.status is INACTIVE at the time of the request, the allocation application service SHALL reject the request with a 4xx HTTP status code, SHALL NOT create or persist any TrainerAllocationResponse (or equivalent allocation record) for that trainer, and SHALL return an ErrorResponse containing a human-readable message that clearly states the trainer is inactive and cannot be allocated.
- [ ] T006 FR-US-004-006 (US-004-ac-4): When an inactive trainer’s status is changed to ACTIVE via POST /trainers/{trainerId}/status, that trainer SHALL once again be included in subsequent GET /trainers results that, by default, list active trainers, subject to any additional filters applied by the client.
- [ ] T007 FR-US-004-007 (US-004-ac-4): After a trainer is reactivated to ACTIVE, any internal trainer eligibility checks performed by the allocation logic backing POST /allocations SHALL consider that trainer as eligible with respect to status, provided that all other allocation constraints (including but not limited to certificationIds, availability, and domainAllocationRules) are satisfied; those other rules are not modified by this story and MUST still be applied.
- [ ] T008 FR-US-004-008 (US-004-ac-5): Each successful trainer status change executed through POST /trainers/{trainerId}/status (i.e., a transition that actually changes the TrainerResponse.status value) SHALL result in an append-only audit event being written via the centralized Audit Logging Component; the audit store MUST NOT allow modification or deletion of existing status-change events via this workflow.
- [ ] T009 FR-US-004-009 (US-004-ac-5): The status-change audit event produced for POST /trainers/{trainerId}/status SHALL be retrievable via both GET /audit/events and GET /trainers/{trainerId}/audit-events and SHALL include, at a minimum, the following fields: module value TRAINER, the trainer recordId, the previous status value, the new status value, actorUserId derived from the authenticated user’s JWT, a timestamp representing when the change was applied, and any reason provided in the TrainerStatusChangeRequest (noting that the exact field names and additional metadata are governed by the centralized audit logging schema).
- [ ] T010 FR-US-004-010 (US-004-ac-6): When a request to change a trainer’s status via POST /trainers/{trainerId}/status is denied due to missing permissions or due to inactive visibility rules, the service SHALL emit a denied-access audit event using the standardized unauthorized access logging semantics so that the attempt is persisted and can be surfaced by GET /security/denied-access.
- [ ] T011 FR-US-004-011 (US-004-ac-6): When POST /allocations is blocked from allocating a trainer because the trainer is inactive and the requesting actor lacks sufficient permissions or visibility (per centralized rules), the service SHALL log a denied-access audit event via the same unauthorized access logging semantics, and this event SHALL be retrievable through GET /security/denied-access for monitoring and investigation purposes.
- [ ] T012 Verify US-004-ac-1: When a client calls POST /trainers/{trainerId}/status with a valid TrainerStatusChangeRequest and the authenticated user has the necessary trainer lifecycle permission, the Training Management Core Service updates only the TrainerResponse.status field between ACTIVE and INACTIVE and preserves all other trainer profile fields unchanged in the underlying trainer repository.
- [ ] T013 Verify US-004-ac-2: When a trainer is set to INACTIVE via POST /trainers/{trainerId}/status, subsequent calls to GET /trainers and any trainer search used internally by POST /allocations must, by default, exclude that trainer from eligibility and list results unless an explicit status or INACTIVE_DATA.VIEW style permission is applied in accordance with centralized visibility rules.
- [ ] T014 Verify US-004-ac-3: When POST /allocations is invoked to allocate a trainer whose TrainerResponse.status is INACTIVE, the allocation application service must reject the request with a 4xx ErrorResponse, not create a TrainerAllocationResponse record, and include a human readable message that clearly indicates the trainer is inactive and cannot be allocated.
- [ ] T015 Verify US-004-ac-4: When an inactive trainer is reactivated through POST /trainers/{trainerId}/status with status ACTIVE, subsequent GET /trainers results and internal allocation eligibility checks backing POST /allocations must again consider that trainer, subject to other eligibility constraints such as certificationIds and availability encoded in domainAllocationRules and related models.
- [ ] T016 Verify US-004-ac-5: Each successful trainer status change performed through POST /trainers/{trainerId}/status must result in an append only audit event written through the Audit Logging Component and exposed via GET /audit/events and GET /trainers/{trainerId}/audit-events, capturing at minimum module TRAINER, the trainer recordId, previous and new status, actorUserId derived from the JWT, timestamp, and any provided reason from TrainerStatusChangeRequest.
- [ ] T017 Verify US-004-ac-6: When a status change or blocked allocation is denied due to missing permissions or inactive visibility rules, the service must log a denied access audit event via the unauthorized access logging endpoint semantics, so that GET /security/denied-access surfaces these attempts for monitoring.
