# Tasks: US-002

## Implementation Tasks
- [ ] T001 FR-US-002-001 (maps AC: US-002-ac-1): The Trainer Application Service MUST expose GET /api/v1/trainers such that, when query parameters for trainer status, OEM certification identifiers, allocation state, location, and/or weekend availability are supplied, the SearchTrainers operation combines all provided filters with logical AND semantics so that the Trainer Repository SearchTrainers returns only trainers that satisfy every specified criterion; behavior when a particular filter parameter is omitted or null is not further constrained by this story and must not be assumed.
- [ ] T002 FR-US-002-002 (maps AC: US-002-ac-2): When the UI supplies a free-text search term in GET /api/v1/trainers, the Trainer Domain Services MUST apply the term against the trainer name, email, and employee identifier fields and then intersect (logical AND) the resulting trainer set with the set obtained from any structured filters; the exact matching behavior (case sensitivity, partial vs exact match, tokenization) is not specified by this story and remains an explicit ambiguity to be resolved elsewhere.
- [ ] T003 FR-US-002-003 (maps AC: US-002-ac-3): Under expected production-scale trainer data volume, the Trainer Repository SearchTrainers operation invoked by GET /api/v1/trainers MUST return the initial page of results within an "agreed performance threshold" as measured by Logging and Monitoring Component metrics, and MUST NOT time out or cause material degradation of other transactional workloads; the precise numeric performance threshold is not defined in this story and must be established outside this specification.
- [ ] T004 FR-US-002-004 (maps AC: US-002-ac-4): When the client requests trainer directory data that includes allocation state indicators, the Trainer Application Service MUST invoke GetTrainerAllocations and use Workshop and Allocation Repository data to derive, for each trainer in the GET /api/v1/trainers response, allocation flags indicating whether the trainer is free, tentative, and/or confirmed; the story does not specify how overlapping or conflicting states are represented and this ambiguity is noted but not resolved here.
- [ ] T005 FR-US-002-005 (maps AC: US-002-ac-5): For each trainer returned by GET /api/v1/trainers, the response model MUST include sufficient identifier and routing information (e.g., trainer unique identifier and any required route key) so that the frontend can navigate directly to the detailed trainer profile view that is backed by CreateTrainer, UpdateTrainer, and GetTrainerById flows, without performing additional API lookups for basic identity fields; the exact set of required fields is not enumerated in this story and remains an implementation detail to be defined consistently across these flows.
- [ ] T006 FR-US-002-006 (maps AC: US-002-ac-6): For users initiating an allocation from the trainer directory, GET /api/v1/trainers MUST return, for each trainer record, the trainer and availability identifiers required to perform downstream POST /api/v1/workshops/{id}/allocate-trainer calls, and the Workshop and Allocation Application Service AllocateTrainer MUST enforce trainer availability and conflict rules prior to confirming any allocation; the detailed availability and conflict rule set is not defined in this story and is treated as an external dependency.
- [ ] T007 FR-US-002-007 (maps AC: US-002-ac-7): Upon completion of each trainer search or filter operation via GET /api/v1/trainers (including successful and, where technically feasible, failed attempts), the HTTP API Controller Layer MUST invoke the Logging and Monitoring Component to emit a structured log entry that includes the authenticated user identity, timestamp, and high-level filter criteria used for the search, and MUST ensure that any sensitive free-text search content is not logged in full but is either omitted or masked according to the applicable logging policy; the story does not specify the exact masking strategy or which portions of free text are considered sensitive, and this remains governed by the external logging policy.

## Verification Tasks
- [ ] T008 Verify US-002-ac-1: When the UI requests trainer directory results via GET /api/v1/trainers with query parameters for status, OEM certification identifiers, allocation state, location, and weekend availability, the Trainer Application Service SearchTrainers query combines all provided filters so that only trainers satisfying every specified criterion are returned from Trainer Repository SearchTrainers.
- [ ] T009 Verify US-002-ac-2: When the UI includes a free text search term (covering trainer name, email, or employee identifier) alongside structured filters in GET /api/v1/trainers, the Trainer Domain Services apply the text term against the appropriate trainer fields and intersect those matches with the structured filter set before returning the paged result to the client.
- [ ] T010 Verify US-002-ac-3: When the trainer dataset volume is at expected production scale, the Trainer Repository SearchTrainers operation executing behind GET /api/v1/trainers must return the initial page of results within the agreed performance threshold, as measured by Logging and Monitoring Component metrics, without timing out or degrading other transactional workloads.
- [ ] T011 Verify US-002-ac-4: When the client requests trainer directory data including allocation state indicators, Trainer Application Service uses GetTrainerAllocations together with Workshop and Allocation Repository data to derive and return per trainer allocation flags for free, tentative, and confirmed states in the GET /api/v1/trainers response model.
- [ ] T012 Verify US-002-ac-5: When a user selects an individual trainer from the directory results and chooses to view the profile, GET /api/v1/trainers responds with enough identifier and routing information for the frontend to navigate to the detailed trainer profile view backed by CreateTrainer, UpdateTrainer, and GetTrainerById flows without additional lookup calls for basic identity fields.
- [ ] T013 Verify US-002-ac-6: When a user selects an individual trainer from the directory results and chooses to initiate an allocation, GET /api/v1/trainers returns trainer and availability identifiers required for downstream POST /api/v1/workshops/{id}/allocate-trainer calls, and Workshop and Allocation Application Service AllocateTrainer enforces availability and conflict rules before confirming the allocation.
- [ ] T014 Verify US-002-ac-7: Whenever a trainer search or filter operation completes through GET /api/v1/trainers, the HTTP API Controller Layer invokes Logging and Monitoring Component to emit a structured log entry including the authenticated user, timestamp, and high level filter criteria used for the search, ensuring any sensitive free text is not logged in full but is either omitted or appropriately masked according to logging policy.
