# Tasks: US-002

The following tasks are ordered and independently reviewable, and they preserve all obligations and gaps from the approved specification. Task wording does not change requirement meaning.

## Implementation Tasks
- [ ] **T001 – Customer existence validation (FR-US-002-001 / US-002-ac-1)**: Implement logic in the `POST /api/v1/orders` handler in service SVC-006 to query the Customer repository using the provided customer ID and proceed to create an order only if a matching customer record exists, leaving the failure-response behavior for a non-existent customer unspecified as per the requirement.
- [ ] **T002 – Product existence validation (FR-US-002-002 / US-002-ac-2)**: Implement logic in the `POST /api/v1/orders` handler in service SVC-006 to query the Product repository using the provided product ID and proceed to create an order only if a matching product record exists, leaving the failure-response behavior for a non-existent product unspecified as per the requirement.
- [ ] **T003 – Quantity validation and 400 handling (FR-US-002-003 / US-002-ac-3)**: Implement quantity validation so that if the requested quantity is less than or equal to zero, the endpoint returns HTTP 400 Bad Request and does not create an order in the Order repository.
- [ ] **T004 – Success response contract within undefined envelope (FR-US-002-004 / US-002-ac-4)**: Ensure that for valid `POST /api/v1/orders` requests where referenced entities exist and quantity validation passes, the endpoint returns an HTTP 2xx success status and a response body that includes at minimum the newly created order ID and order details, without constraining the exact 2xx code or full payload shape beyond what is stated in the requirement.
- [ ] **T005 – Prevent persistence on invalid inputs (FR-US-002-005 / US-002-ac-5)**: Ensure that for all `POST /api/v1/orders` requests that fail due to invalid inputs (including but not limited to the validations described), no order record is persisted in the Order repository.

## Security and Quality Tasks
- [ ] **T006 – Security review against acceptance criteria**: Validate credential and personal-data handling for the `POST /api/v1/orders` flow against the story's acceptance criteria, documenting any assumptions due to unspecified behaviors.
- [ ] **T007 – Accessibility and user-flow verification**: Verify the changed user flow (where applicable in UI or API consumer experience) against the stated accessibility criteria, noting that some aspects of the flow (e.g., failure messaging for missing customer/product) are unspecified in the requirements.
